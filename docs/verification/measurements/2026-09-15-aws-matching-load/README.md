# AWS 매칭 동시성 검증 기록

## 목적

AWS의 분리된 앱 서버와 부하 생성 서버에서 3,000명의 합성 사용자가 동시에 매칭 요청을 보낼 때,
요청 수락률과 최종 매칭 정합성을 확인한다.

이 기록은 전용 테스트 환경의 결과이며, 실제 서비스 이용자 수나 운영 성능 보장으로 해석하지 않는다.

## 조건

- 대상: 매칭 요청 API
- 동시 가상 사용자: 3,000명 (남성 1,500명, 여성 1,500명)
- 요청 방식: 각 사용자가 1회 동시 요청
- 환경: AWS 서울 리전의 전용 앱 서버와 분리된 부하 생성 서버
- 데이터: 테스트 실행 때마다 새로 생성한 합성 사용자·인증 토큰·MySQL·Redis 데이터
- 반복: 3회. 각 회차 전 Redis와 합성 데이터를 초기화

## 결과

| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 3,000 | 3,000 (100%) | 0건 | 468.76 req/s | 5.98초 | 6.16초 | 통과 |
| 2 | 3,000 | 3,000 (100%) | 0건 | 658.90 req/s | 3.99초 | 4.19초 | 통과 |

세 회차 모두 최종 검증 결과는 동일했다.

- 생성된 방: 500개
- 배정 사용자: 3,000명
- 남성·여성 대기열 잔여: 각 0명
- 잘못된 배정: 0건

## 해석 시 주의점

부하 도구의 `initial_matched`와 `initial_waiting`은 API 응답 시점의 상태다. 요청은 즉시 수락되고,
후속 FIFO 매칭이 비동기로 완료될 수 있으므로 이 값만으로 최종 미매칭 인원을 판단하지 않는다.
본 검증의 최종 판정은 실행 이후 Redis에서 확인한 방 수, 전체 배정 수, 잔여 대기열, 잘못된 배정 수다.

## 개선 전 단일 구성 한계 탐색

3회 재현 검증 뒤 같은 전용 환경에서 사용자를 단계적으로 늘렸다. 이 시점의 `actors.json`은
남성 사용자 뒤에 여성 사용자를 생성한 순서였으므로, 아래 결과는 **성별 입장 순서가 섞인
검증 결과가 아니다**.

| 동시 사용자 | 결과 | 처리량 | p95 응답 시간 | 최종 상태 |
| ---: | --- | ---: | ---: | --- |
| 6,000 | 성공 | 910.80 req/s | 5.87초 | 1,000개 방, 6,000명 전원 배정, 대기열 0명 |
| 9,000 | 포화 | 295.27 req/s | 9.82초 | 연결 재설정 발생, 7,584명 배정, 51명 대기 |

9,000명에서는 808건의 HTTP 연결 실패(약 8.98%)가 발생했고, 30초를 추가로 기다린 뒤에도
최종 상태가 회복되지 않았다. 이 결과를 개선 전 기준선으로 삼아 연결 수용량, 대기열 정리,
고빈도 로그를 보완하고 성별 입장 순서를 무작위화한 뒤 다시 검증했다.

## 개선 후 혼합 순서 9,000명 재현 검증

### 변경 범위

- Tomcat 연결·대기열·작업 스레드 한도를 전용 부하 환경에서 조정했다.
- 만료 대기자를 정리할 때 전체 대기열을 매 요청마다 재구성하지 않고, 만료된 사용자만 제거하도록 Redis Lua 로직을 변경했다.
- 매칭 요청 경로의 고빈도 INFO 로그를 DEBUG로 낮췄다.
- 합성 사용자 목록을 암호학적으로 섞고, 실행마다 목록 SHA-256 다이제스트를 기록했다. 따라서 남녀가 한 성별씩 뭉쳐 들어가는 입력 순서를 피했다.

### 조건

- 대상: `POST /api/session/enter` 1회 요청
- 동시 가상 사용자: 9,000명 (남성 4,500명, 여성 4,500명)
- 환경: AWS 서울 리전의 단일 앱 서버(Spring Boot·MySQL·Redis)와 분리된 단일 부하 생성 서버
- 매 회차 전 Redis·MySQL 합성 데이터를 초기화하고, 새로 섞은 사용자 목록을 생성했다.
- 최종 판정: Redis에서 1,500개 완전한 방, 9,000명 배정, 남녀 대기열 0명, 잘못된 배정 0건을 확인한다.

### 결과

| 회차 | 요청 수락 | HTTP 실패 | 처리량 | p95 응답 시간 | p99 응답 시간 | 최종 정합성 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 9,000 (100%) | 0건 | 920.30 req/s | 8.94초 | 9.09초 | 통과 |
| 2 | 9,000 (100%) | 0건 | 1,106.03 req/s | 7.36초 | 7.52초 | 통과 |
| 3 | 9,000 (100%) | 0건 | 1,109.68 req/s | 6.34초 | 6.49초 | 통과 |

세 회차 모두 1,500개 방에 9,000명 전원 배정됐고, 남성·여성 대기열 잔여와 잘못된 배정은 0건이었다.

### 해석

개선 전 9,000명 시험의 HTTP 실패율 8.98%와 달리, 개선 후 혼합 순서 시험 3회는 모두 HTTP 실패율 0%와 최종 정합성 통과를 기록했다. 다만 이 결과는 연결 수용량·Redis 정리 방식·로그 수준·입력 순서를 **함께** 바꾼 뒤의 종합 결과다. 단일 변경이 어느 정도 효과를 냈는지까지 분리해 증명한 실험은 아니다.

이 수치는 단일 앱 서버의 HTTP 매칭 API 검증 결과다. 브라우저 실제 사용, OpenVidu·TURN 영상/음성 미디어 트래픽, AI 처리, 다중 인스턴스·로드 밸런서 장애 전환, 운영 SLA를 뜻하지 않는다.

## 포트폴리오에 사용할 수 있는 사실 문장

> AWS 분리 환경에서 합성 사용자 3,000명의 동시 매칭 요청을 3회 재현 검증했습니다. 모든 회차에서 요청 수락률 100%, HTTP 실패 0건을 확인했고, 최종적으로 500개 방에 3,000명 전원 배정, 잔여 대기열 및 잘못된 배정 0건을 검증했습니다. p95 응답 시간은 3.92~5.98초였습니다.

> 단일 AWS 앱 서버와 분리된 부하 생성 서버에서, 남녀 합성 사용자 9,000명의 입장 순서를 매 회차 무작위화해 동시 매칭을 3회 검증했습니다. 세 회차 모두 HTTP·애플리케이션 수락률 100%, 최종 1,500개 방·9,000명 전원 배정, 잔여 대기열 및 잘못된 배정 0건을 확인했습니다. p95 응답 시간은 6.34~8.94초였습니다. 이 검증은 영상·음성 미디어나 다중 인스턴스를 포함하지 않은 단일 서버 HTTP 매칭 범위입니다.
