## 확인하고 수정한 문제

### 인증·대기열

- 일반 얼굴 인증 경로는 `auto=true`가 없으면 대기열 진입이 실행되지 않았다. 테스트 전용 URL 토큰도 실제 로그인 토큰을 덮어쓸 수 있었다.
- 취소가 화면 이동만 수행하던 경로를 서버 취소와 연결했다. 입장 응답을 기다린 뒤 취소하며 실패 시 재시도할 수 있다.
- 대기 순번을 전체 인원처럼 표시하던 계산을 성별별 대기 인원 조회로 교체했다.
- 전역 requestId 인증 결과를 `verify:{userId}:{requestId}`로 분리했다. 타인의 결과 사용과 완료·소비 후 늦은 결과의 부활을 차단했다.
- PENDING 결과 조회는 보존하고 VERIFIED만 원자적으로 소비한다.
- 기존 방 확인, 인증 소비, 대기열 등록, 3대3 매칭을 하나의 Lua 실행에 묶었다. 동시 요청으로 이미 매칭된 사용자가 다시 등록되거나, 뒤 순번 요청자가 다른 사람의 방을 받는 문제를 막았다.
- 대기 중 폴링이 30초 이상 끊긴 자리는 다음 대기열 처리에서 제외한다. 다시 입장하려면 얼굴 인증이 필요하다.
- Lua가 저장한 해시를 문자열로 읽도록 멤버 조회 직렬화를 맞췄다.

### 미팅 단계·종료

- 화면이 바뀌는 시점과 타이머가 시작되는 시점을 분리했다. 프런트는 START_TIMER 수신 후에만 시간을 줄인다.
- 같은 자기소개 단계가 반복되어도 stageSequence로 각 차례를 구별한다.
- 이전 단계의 준비 응답·타임아웃·중복 타이머는 다음 단계에 영향을 주지 않는다.
- 탭의 타이머 실행이 늦어지면 실제 경과 시간으로 표시를 보정한다. 서버와 기기 간 절대 시각 동기화나 전송 지연 보정까지 구현한 것은 아니다.
- 얼굴 공개 시간의 서버·메시지 불일치와 조기 room.reset을 제거했다. 얼굴 공개가 실제 끝난 후 연결·Redis·레지스트리를 정리한다.

### 인증 경계·화상 연결

- 인증 필터가 컨트롤러 예외까지 잡아 같은 요청을 두 번 실행하거나 인증 오류로 바꾸지 않도록 예외 경계를 좁혔다.
- 방 멤버 조회는 해당 방 참가자에게만 허용한다.
- API 헤더, WebSocket URL 쿼리, OpenVidu 토큰을 직접 출력하던 애플리케이션 로그를 제거했다. 모든 인프라 로그를 감사한 것은 아니다.
- 여러 API의 401 응답은 하나의 갱신 요청을 공유하고 비즈니스 오류 응답 정보는 보존한다.
- Refresh Token에는 없는 role을 Access Token 검증에서 요구하여 재발급용 토큰의 일반 API·WebSocket 사용을 차단했다. 테스트 토큰도 운영 발급 형식에 맞췄다.
- 화상 접속 중 같은 요청이 반복되어도 connect/publish를 중복 실행하지 않는다. 이전 연결의 늦은 완료·이벤트와 언마운트 후 카메라 완료 결과를 무시하고 자원을 정리한다.
- Publisher에는 마스킹 트랙의 복제본을 넘겨 원본 스트림이 세션 전환으로 종료되지 않도록 했다.
- 단체방 복귀 시 서버가 사용자별 새 토큰을 MEDIA_SESSION으로 보내며 이미 사용한 JOIN_OK 토큰을 재사용하지 않는다. OpenVidu v2 Connection 토큰 재사용 제한은 [공식 REST 문서](https://docs.openvidu.io/en/2.20.0/reference-docs/REST-API/)로 교차 확인했다.

## 남은 위험과 배포 차단 판단

1. **P1 — 매칭 직후 이탈 복구:** 대기열 취소와 매칭이 동시에 일어나 이미 방이 배정된 경우, 아직 WebSocket에 오지 않은 사용자의 자리를 해제하는 정책이 없다. 6명 중 일부가 오지 않는 방의 입장 제한시간·취소/재매칭 정책을 확정하고 테스트해야 한다.
2. **P1 — 재접속 복구:** 새로고침·네트워크 단절 후 현재 미팅 단계, 남은 시간, 파트너와 새 미디어 토큰을 복구하는 end-to-end 경로가 미완성이다. 이번 수정은 오래된 콜백 방지이지 자동 재접속 완성이 아니다.
3. **P1 — 실제 미디어·운영 검증:** 공개 HTTPS, Kakao OAuth, OpenVidu/TURN과 서로 다른 네트워크의 6인 카메라/마이크 E2E는 미검증이다. AWS 카드 인증 거절은 사용자 제공 상태이며 계정에 직접 변경하지 않았다.
4. **P1 — 의존성 보안 분류:** npm audit --omit=dev는 high 13, moderate 5(합계 18)를 보고했다. axios/react-router 및 OpenVidu 하위 의존성이 포함된다. 패키지 분류 때문에 빌드 도구도 보고되어 실제 브라우저·운영 이미지 도달성을 별도로 판단해야 한다. 자동 강제 업그레이드는 하지 않았다. 무조건 취약점 0 또는 안전한 공개 서비스라고 주장할 수 없다.
5. **P2 — 구형/미완성 UI:** 전체 린트 잔여 오류와 Step4_Talk의 목업 취향 정보가 남아 있다. 실사용자 정보로 오인하지 않도록 후속 정리가 필요하다.
6. **P2 — 운영 상태·자원:** 방·타이머는 단일 JVM 메모리에 의존한다. 다중 Pod, 프로세스 재시작 중 미팅 복구, OpenVidu 하위 세션 캐시의 장기 정리는 별도 검증 대상이다.
7. **P2 — 민감정보와 측정:** 실제 얼굴 비교 정확도, 동의·보관·탈퇴 시 폐기, 백업 복원, 부하·지연·CPU/메모리 측정은 완료로 판정하지 않았다. 빌드 번들은 JS 약 849 kB(gzip 259 kB)로 크기 경고가 남아 있다.

## 반영 순서와 호환성

- 기능별 PR 텍스트는 [PR 복사 문서](./review-prs-2026-09-07.md)를 사용한다.
- 브랜치 순서대로 검토한다. merge commit 방식은 부모 커밋을 보존한다. squash/rebase merge를 선택하면 다음 브랜치의 기준을 정리한 뒤 PR을 열어 중복 diff를 방지한다.
- Redis 인증 키 형식과 대기열 lease, stageSequence/MEDIA_SESSION 계약이 바뀌므로 **진행 중인 미팅이 없는 상태에서 프런트·백엔드를 함께 배포**해야 한다.
- 과거 Redis 키나 운영 데이터는 이번 리뷰에서 삭제하지 않았다. 기존 인증/대기 상태의 만료·재인증을 안내한다.
- 수정분 원격 CI → 운영 이미지 재빌드·리허설 → 이탈/복구 경계 보완 → 실제 6인 E2E 순으로 확인한다.
