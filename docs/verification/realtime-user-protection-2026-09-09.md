# 실시간 사용자 보호 보강 — 2026-09-09

## 목적과 범위

실시간 영상방에서 서버가 매칭 권한을 다시 확인하고, 퇴장 뒤 발급된 미디어 연결을 무효화하며, 과도하거나 잘못된 입력이 방 상태를 소모하지 않게 한다. 이 문서는 로컬 구현과 테스트 범위를 기록한다. 공개 배포, 외부 TURN, 실제 사용자·카메라·마이크 데이터, 금융 규제 준수 주장은 포함하지 않는다.

## 구현 전 확인된 위험

1. WebSocket 핸드셰이크는 Redis의 `currentRoom`과 멤버 키를 확인했지만, 핸드셰이크와 `JOIN_ROOM` 처리 사이에 매칭이 정리될 경우 토큰 발급 전에 같은 확인을 다시 하지 않았다.
2. 방이 비면 OpenVidu 세션 캐시만 제거했고, 개인 퇴장은 메모리 참가자만 제거해 Redis 방 권한이 남을 수 있었다. 서버의 OpenVidu 세션 또는 아직 사용하지 않은 연결 토큰을 직접 무효화하지 않았다.
3. WebSocket은 메시지 크기와 짧은 시간의 반복 전송을 제한하지 않았다. 게임 투표 파싱 실패는 표준 오류 출력으로 남을 수 있었다.
4. 쪽지는 참여자 확인은 했지만 내용 길이·빈도·조회 크기 상한이 없었다. OpenVidu HTTP 오류 본문은 로그에 남길 수 있었다.

## 변경 결정

- `currentRoom`, 방 멤버 Set, 멤버 Hash를 모두 확인하는 `hasActiveRoomAccess`를 추가하고, 방 정보 조회와 토큰 발급 직전에 사용한다.
- OpenVidu REST의 Connection 삭제로 사용자의 발급 연결을 무효화하고, 방 종료 시 Session 삭제로 남은 연결 전체를 종료한다. 개인 퇴장·영구 연결 해제는 Redis의 멤버·멤버 Hash·현재 방 권한을 원자적으로 회수한다. OpenVidu 요청 실패는 토큰·응답 본문 없이 서버 로그에만 요약한다.
- WebSocket은 4 KiB 초과 메시지와 세션당 10초에 20건을 초과한 메시지를 역직렬화 전에 거절한다.
- 쪽지는 공백 제외 1~1,000자, 사용자당 10초에 5건으로 제한하고 목록 요청은 최대 100건으로 제한한다. 이 빈도 제한은 단일 앱 인스턴스 메모리 기준이며, 다중 인스턴스 전역 제한은 별도 운영 과제다.

## 검증 목표

- 매칭 멤버가 아닌 사용자와 정리된 매칭 사용자는 방 정보·WebSocket 입장·영상 토큰을 받지 못한다.
- 정상 매칭 사용자는 기존 JOIN 흐름으로 토큰을 받고 입장한다.
- 퇴장 또는 방 종료 후 OpenVidu Connection/Session 삭제를 요청한다.
- 비정상 크기·반복 WebSocket 입력과 과도한 쪽지 입력은 안전한 오류로 거절되고 원문·토큰은 응답에 포함하지 않는다.

## 남은 경계

- 실제 인터넷 환경의 OpenVidu 서버에서 Connection/Session 삭제 이벤트까지의 E2E는 공개 배포와 함께 별도 검증한다.
- 현 메모리형 제한기는 다중 인스턴스에서 공유되지 않는다. Redis 기반 전역 제한은 배포 토폴로지 확정 후 별도 구현한다.
- 발급한 OpenVidu Connection 참조도 현재 애플리케이션 메모리에 보관한다. 백엔드 재시작 뒤의 미사용 토큰 회수·재시도는 OpenVidu 서버 E2E 및 재시작 복구 정책과 함께 보강해야 한다.
- 토큰 자체를 가진 사용자의 OpenVidu 직접 접속은 애플리케이션 HTTP/WebSocket 인가와 별개이므로, 이번 변경은 퇴장 시 Connection 삭제·방 종료 시 Session 삭제 요청으로 회수한다. 실제 OpenVidu 서버의 삭제 성공 재시도·관측은 배포 전 검증 과제로 남는다.

## 재개 지점

외부 배포 승인 후 실제 OpenVidu 서버에서 ① 권한 없는 방 ID로 WebSocket 연결 거절, ② 퇴장 뒤 기존 미디어 연결의 `forceDisconnectByServer` 또는 pending-token 무효화, ③ 방 종료 뒤 Session 삭제를 독립 브라우저 두 개 이상으로 확인한다. 다중 인스턴스를 도입하면 WebSocket·채팅 빈도 제한을 Redis 등 공유 저장소로 옮긴다.
