# Roundy 6인 E2E·안정성 측정 계획

이 문서는 배포 전후에 같은 방식으로 핵심 미팅 흐름과 서비스 복구 시간을 측정하기 위한 기준입니다. 결과가 없는 항목은 완료로 표시하지 않습니다.

## 측정 원칙

- 실행마다 Git 커밋, 날짜, 환경, 결과를 기록합니다.
- 테스트 참여자는 이름 대신 `A`~`F`로 기록합니다.
- 얼굴 이미지·영상, 카카오 토큰, 전화번호, 실명은 결과 문서와 Git에 저장하지 않습니다.
- 실제 얼굴 비교는 참여자의 동의와 별도 보관·폐기 기준이 정해진 경우에만 수행합니다.
- 수치가 1회 측정이면 `1회 측정`이라고 명시하고, 전후 비교는 같은 환경에서만 합니다.

## 1. 통합 환경 준비 시간

### 측정 방법

```bash
started_at=$(date +%s)
docker compose --env-file .env up -d --build
./scripts/wait-for-local-ready.sh --env-file .env --started-at "$started_at"
```

`READY_SECONDS`는 시작 시각부터 MySQL, Redis, MinIO, OpenVidu 개발 서버, AI, 백엔드, 프런트가 모두 healthy이고 세 개의 HTTP 헬스체크가 200이 될 때까지 걸린 시간입니다.

첫 실행은 이미지 빌드와 AI 모델 캐시 유무의 영향을 받으므로, 다음 두 조건을 분리합니다.

| 측정 ID       | 조건                           | 커밋   | READY_SECONDS | 결과   |
| ------------- | ------------------------------ | ------ | ------------- | ------ |
| START-COLD-01 | 이미지·AI 캐시가 없는 첫 실행  | 미측정 | 미측정        | 미측정 |
| START-WARM-01 | 이미지와 AI 캐시가 있는 재실행 | 미측정 | 미측정        | 미측정 |
| START-WARM-02 | 동일 조건 재실행               | 미측정 | 미측정        | 미측정 |
| START-WARM-03 | 동일 조건 재실행               | 미측정 | 미측정        | 미측정 |

## 2. 백엔드 복구 시간

### 측정 방법

진행 중인 미팅이 없는 로컬 환경에서만 수행합니다.

```bash
restarted_at=$(date +%s)
docker compose --env-file .env restart backend
./scripts/wait-for-local-ready.sh --env-file .env --started-at "$restarted_at"
```

이 측정은 **백엔드 readiness 복구 시간**만 의미합니다. 현재 미팅 방 상태는 백엔드 메모리에 있으므로, 재시작 후 진행 중이던 미팅이 복구된다는 의미가 아닙니다.

| 측정 ID             | 커밋   | READY_SECONDS | 데이터 보존 확인 | 결과   |
| ------------------- | ------ | ------------- | ---------------- | ------ |
| RECOVERY-BACKEND-01 | 미측정 | 미측정        | 미측정           | 미측정 |
| RECOVERY-BACKEND-02 | 미측정 | 미측정        | 미측정           | 미측정 |
| RECOVERY-BACKEND-03 | 미측정 | 미측정        | 미측정           | 미측정 |

## 3. 6인 핵심 미팅 E2E

### 사전 조건

- 독립된 테스트 계정 6개와 브라우저 세션 6개
- 대기열 조건에 맞는 테스트 프로필 3명씩
- 카카오 로그인, 얼굴 인증, OpenVidu 연결에 필요한 운영 또는 로컬 설정
- 미팅 중단 시 원인과 시각을 기록할 진행자 1명

### 성공 기준

각 실행에서 다음을 모두 만족해야 `성공`입니다.

1. 6명이 인증을 마치고 대기열에 입장합니다.
2. 서버가 방을 만들고 모든 참여자가 WebSocket과 OpenVidu 세션에 연결합니다.
3. 프런트가 서버의 `STAGE_CHANGE` 이벤트에 맞춰 실제 미팅 화면을 전환합니다.
4. `BREAK` 메시지는 새 미팅 화면이 아니라 대기 안내로 처리됩니다.
5. 선택한 미팅 모드의 자기소개·투표·로테이션·게임(해당 시)·결과 단계를 모두 마칩니다.
6. 상호 선택한 한 쌍은 매칭 결과를 받고, 상호 선택이 아닌 참여자는 매칭되지 않습니다.
7. 브라우저 치명 오류, 서버 예외, 수동 DB 수정 없이 종료합니다.

`FACE_REVEAL`은 실제 상호 매칭이 만들어진 경우에만 별도 성공 기준으로 기록합니다.

| 실행 ID   | 커밋   | 참여자 수 | 단계 전환 완료 | 상호 매칭 검증 | 치명 오류 | 결과   |
| --------- | ------ | --------: | -------------- | -------------- | --------- | ------ |
| E2E-6P-01 | 미측정 |         0 | 미측정         | 미측정         | 미측정    | 미측정 |
| E2E-6P-02 | 미측정 |         0 | 미측정         | 미측정         | 미측정    | 미측정 |
| E2E-6P-03 | 미측정 |         0 | 미측정         | 미측정         | 미측정    | 미측정 |

## 포트폴리오 문장 기준

다음 문장은 표의 실제 결과가 채워진 뒤에만 사용합니다.

- 기동 측정: “동일 환경의 warm start 3회에서 7개 서비스 healthy와 핵심 헬스체크 200까지의 시간을 측정했다.”
- 복구 측정: “백엔드 재시작 뒤 readiness 복구 시간을 3회 측정하고, 진행 중 미팅 상태의 외부화가 필요하다는 한계를 분리해 관리했다.”
- E2E: “테스트 사용자 6명으로 인증부터 상호 매칭까지의 핵심 흐름을 3회 반복 검증해 `성공 횟수/실행 횟수`를 확인했다.”

모든 수치는 실제 표의 값으로 바꿉니다. 공개 배포 전 로컬 측정값을 운영 성과로 표현하지 않습니다.
